## Главная идея

Сохранить продукт вокруг любимых маршрутов и привычных остановок посадки.
У каждого маршрута должны быть собственные направления, а у каждого направления —
сохранённая остановка. Общая лента нескольких подходящих автобусов должна сохраниться:
сейчас это полезное свойство пары 380/316.

Главный экран отвечает на вопрос «когда мой следующий автобус?». Каталог TTC нужен
для добавления в избранное. Открывать каталог при каждом запуске не требуется.

## Что уже стоит сохранить

- Расписание доступно из локальных данных; live-данные дополняют его.
- Общая лента 380/316 помогает выбрать ближайший подходящий автобус.
- Направление и остановка согласованы между отправлениями и расписанием.
- Запросы live-данных зависят от активности нативного экрана; карта обновляется чаще главной.
- Есть обработка отсутствующих данных, деморежимы и журнал запросов.
- Android-виджет работает по расписанию без сети на нативной стороне.
- Уже есть тесты расписания, live-сопоставления, геометрии и локализации.

## Упрощение экранов

| Экран | Предложение |
| --- | --- |
| Запуск | После первоначальной настройки открывать избранное. Для одного маршрута можно сразу открыть его отправления. Геопозиция предлагает ближайшую остановку, ручной выбор остаётся главным при неоднозначности. |
| Главная | Короткие карточки избранных маршрутов: номер, направление, остановка, ближайшее прибытие, источник и свежесть. Нажатие открывает подробности. Добавление и изменение порядка находятся здесь. |
| Подробности | Сохранить крупную карточку следующего автобуса, показать несколько ближайших отправлений. Полный день доступен через расписание. Направление переключается для текущего маршрута. |
| Общая лента | Позволить объединить взаимозаменяемые варианты, например 380/316 «В Коджори». У каждого участника группы свои направление и остановка; совместимость не следует из одинакового номера направления. |
| Карта | Сначала выбранный маршрут или группа; остальные избранные включаются явно. Область камеры определяется геометрией выбранных маршрутов. Ошибка одного маршрута не скрывает остальные. |
| Расписание | Сначала сохранить отдельный быстрый доступ. Добавить выбор даты: сегодня, завтра, календарь. При нескольких маршрутах фильтр строится из выбранных данных. Удаление вкладки стоит решать после проверки ежедневного сценария. |
| Настройки | Компактный список параметров, управление избранным — на главной. Техническую диагностику раскрывать по необходимости. |
| Виджет | Выбор избранного маршрута или группы и остановки; отображение сохранённого расписания. Для нового формата нужны миграция payload и поддержка нативных клиентов. |

### Конкретно настройки

Сейчас оформление, язык и данные доступны через верхние summary-карточки и через
карточки разделов. Внутри раздела данных пользователь видит расписания, остановки,
геометрию, число запросов, прогресс, даты кеша и встроенного набора.

Предлагаемая структура:

1. **Язык** — отдельная короткая строка.
2. **Оформление** — тема и палитра, компактный выбор с предпросмотром.
3. **При запуске** — последнее избранное / весь список; подсказка ближайшей остановки отдельно от способа открытия.
4. **Виджеты** — добавить и выбрать содержимое.
5. **Данные офлайн** — «готовы / обновляются / частично доступны», дата обновления и одна кнопка обновления.
6. **О приложении** — версия, поддержка, документы; диагностика внутри дополнительного раздела.

Настройку посадки и направления лучше делать при добавлении маршрута и из его карточки.
Раздельные refresh-кнопки для геометрии и остановок, TTL и счётчики запросов можно
оставить в диагностике. Свежесть live-данных должна быть видна там, где показано прибытие.

## Что мешает произвольным маршрутам

- `BusLine` выводится из константы с двумя маршрутами в `ttc.ts`.
- Несколько расчётов принимают отдельные аргументы `schedule380` и `schedule316`.
- `toKojori/toTbilisi` используется как общая система направлений во всём приложении.
- Остановки разных маршрутов объединяются по общему направлению, теряя принадлежность.
- Query keys геометрии и позиций содержат общее направление вместо конкретного маршрута и pattern.
- `useLocation` классифицирует координаты как Коджори или Тбилиси.
- Карта ограничена коридором Коджори–Тбилиси; цвета и фильтры рассчитаны на два автобуса.
- В baked-данных, сборочных скриптах, Android и iOS виджетах также есть фиксированные 380/316.
- Особые правила первой остановки и доверия live-прогнозам привязаны к этим маршрутам.

Простое расширение `ROUTES` не решит эти ограничения.

## Целевая модель

```ts
type RoutePatternRef = {
  routeId: string;
  patternSuffix: string; // Идентифицируется вместе с routeId.
};

type FavoriteRoute = {
  id: string;
  routeId: string; // Номер автобуса — отображаемый атрибут, не основной ключ.
  order: number;
  preferredPatternSuffix: string;
  boardingStopByPattern: Record<string, string>;
};

type FavoriteGroup = {
  id: string;
  title: string;
  members: {
    favoriteRouteId: string;
    pattern: RoutePatternRef;
    stopId: string;
  }[];
};
```

Каталог хранит маршруты, доступные patterns, их назначения и последовательности
остановок. Избранное хранит пользовательский выбор. Группы — дополнительное удобство:
добавление одного маршрута не должно требовать создания группы.

Нельзя считать `0:01` универсальным «туда», а `1:01` — «обратно»: уже для 380 и 316
соответствие противоположное. Количество patterns также не стоит фиксировать равным двум.
Остановка допустима только для конкретного pattern. Если она исчезла после обновления,
нужно предложить замену, сохранив само избранное.

Первое добавление: поиск по номеру/названию → маршрут и направление → остановка →
«В избранное». Обратное направление настраивается по желанию. Пустое избранное —
нормальное состояние с кнопкой добавления; удаление можно отменить.

### Модули и интерфейсы

- **Каталог маршрутов:** поиск и получение маршрута с patterns и остановками.
- **Избранное:** добавление, порядок, остановки посадки, миграция и проверка допустимости.
- **Отправления:** один интерфейс для любого набора route/pattern/stop, возвращающий
  ближайшие рейсы, источник, свежесть и ошибки каждого участника. Внутри — кеш,
  выбор календарного периода, live-сопоставление и особенности TTC.
- **Снимок виджета:** построение версионированного локального представления из того же
  расчёта расписания, пригодного для нативного отображения без сети.

Такая глубина модулей убирает необходимость экранам самим собирать расписания,
разбирать сбои каждого запроса и знать исключения отдельных остановок.
Новый маршрут добавляется данными каталога и пользовательским выбором.

Особенности Коджори нужно сохранить как точечные правила для соответствующих
маршрутов/patterns/остановок, с безопасным поведением по умолчанию для остальных.
Разные города и дополнительные транспортные провайдеры пока не требуют абстракций.
Поддержку разных видов транспорта TTC следует включать по фактически доступным данным.

## Оптимизация при росте избранного

Сейчас главная рисует все ближайшие отправления через `ScrollView` и `.map()` с
горизонтом 23 часа. Для частых маршрутов список существенно вырастет. Показать короткий
список на главной; длинные списки избранного и расписания виртуализировать.

Карта сейчас запрашивает позиции каждого из двух маршрутов раз в 5 секунд. При
механическом расширении до N маршрутов получится примерно N/5 запросов в секунду,
без учёта повторов и длительности запросов. Число сохранённых маршрутов не должно
равняться числу постоянно опрашиваемых маршрутов.

- Загружать live-данные для видимых карточек и выбранных маршрутов карты.
- Делить запрос arrivals между избранными вариантами с одной остановкой.
- Кешировать расписания и геометрию по `routeId + patternSuffix`, а не по всему списку избранного.
- Выдавать данные частями, учитывать ошибки и свежесть каждого маршрута.
- Ограничивать одновременные запросы, делать backoff при сбоях TTC.
- Скачивать статические данные добавленных маршрутов по необходимости; существующий
  baked-набор сохранить как стартовый набор Коджори.
- Геопозицию и её получение делить между потребителями; текущий `useLocation` создаёт
  состояние и подписки в каждом вызове. Эффект на GPS и батарею сначала измерить.

Нативные лаги и расход батареи здесь не измерялись. Проверять нужно release-сборку
на Android: время открытия, переключение вкладок, память, кадры карты, число запросов
и обращений к геолокации. Много ручных `useMemo` и 57 lint-предупреждений — повод для
точечного разбора, но сами по себе не доказательство проблем производительности.

доступен офлайн и в виджете. Наборы из 0, 1, 2 и 10+ избранных не требуют правок кода.
Старый выбор 380/316 сохраняется. Ошибка одного участника группы не скрывает остальные.
Публикация и релиз не входят в этот проход.

1. **Надёжность:** точечная очистка кеша, обновление данных независимо от настроек,
   частичные ошибки, даты рейсов и синхронизация виджета.
2. **Новая модель под текущим интерфейсом:** расчёты по массиву маршрутов,
   route/pattern-ключи, миграция настроек; сохранить нынешний сценарий 380/316.
3. **Каталог и избранное TTC:** добавление третьего произвольного маршрута,
   направления и остановки, удаление/порядок/пустое состояние, загрузка офлайн-данных.
   До реализации проверить ответы каталога и patterns: текущая документация проекта
   описывает каталог, но в этом аудите его живой контракт не проверялся.
4. **Интерфейс и масштабирование:** компактные настройки, карточки избранного,
   выбранные маршруты на карте, сохранение общей ленты 380/316 и группы при необходимости.
5. **Виджеты:** произвольное избранное в Android/iOS, миграция существующих экземпляров,
   сохранение работы без нативных сетевых запросов.

Критерии готовности: 1, 2 и 10+ избранных; третий маршрут добавляется без изменения
кода; доступные данные не пропадают из-за одного сбоя; выбор сохраняется после
перезапуска и очистки TTC-кеша; офлайн и переход суток/выходных работают; старые
избранные остановки и виджеты переживают миграцию.
